# «Уход за близким»: план безопасного внедрения

Статус: подготовка к реализации. Не включать на production до проверки доступа и миграций.

## Принцип
Дневник ухода — **отдельный профиль подопечного**, а не записи в основном профиле владельца аккаунта. Не использовать текущие таблицы персонального дневника без идентификатора подопечного. Не записывать медицинские данные в localStorage, аналитику или браузерные логи.

## MVP интерфейс (iPhone first)
1. Список подопечных («Добавить близкого»), понятное имя/псевдоним; информация о согласии подопечного и законных основаниях обработки.
2. Карточка «Сегодня»: большие кнопки «Давление», «Лекарство», «Питание/вода», «Гигиена», «Положение тела», «Самочувствие», «Заметка», «Посещение помощника».
3. Каждая запись: дата/время (с возможностью исправить), тип события, значения, необязательная заметка, кто внёс; редактирование/удаление.
4. Хронология с фильтрами, напоминания только по явной настройке, экспорт PDF для врача. Никаких автоматических медицинских назначений.
5. Информирование об экстренных признаках инсульта: при внезапном ухудшении речи, слабости, асимметрии лица — вызвать экстренную помощь, не ждать ответа приложения.

## Модель данных для проектирования миграции (не запускается автоматически)
- care_recipients: id uuid PK, owner_user_id uuid NOT NULL, display_name text NOT NULL, consent_recorded_at timestamptz NULL, created_at, updated_at.
- care_events: id uuid PK, recipient_id uuid FK, created_by uuid NOT NULL, event_at timestamptz NOT NULL, category enum/check (bp, medication, meal, hydration, hygiene, position, wellbeing, caregiver_visit, note), payload jsonb NOT NULL, notes text, created_at, updated_at.
- Для давления: systolic/diastolic/pulse числовые, валидация диапазонов и единицы измерения; для лекарств название, дозировка текстом, факт приема; без автоматического назначения дозы.
- Отдельная таблица разрешений/ролей потребуется лишь для семейного совместного доступа во второй версии.

## Безопасность и критерии приемки
- Supabase RLS включена для **каждой** новой таблицы; policy SELECT/INSERT/UPDATE/DELETE проверяет auth.uid() = owner_user_id или JOIN care_recipients.owner_user_id.
- Запрет доступа между владельцами проверен тестами с двумя пользователями; клиент не должен доверять owner_user_id из формы.
- При выключенной/приостановленной Supabase показывать внятное сообщение «Не удалось подключиться. Запись не сохранена»; не показывать успешное сохранение до ответа сервера.
- Не включать реальные данные подопечного в демонстрационные/тестовые записи или PR.
- Проверить миграции и откат, обработку ошибок, мобильные экраны, экран пустого состояния, локализацию на русский, PDF на кириллице.
- Перед публикацией убедиться, что проект Supabase возобновлен, вход работает, разрешения на обработку данных оформлены.

## Этапы
1. Проверка текущих таблиц, роутов, auth и Supabase, восстановление доступности.
2. Миграция + RLS + тесты изоляции.
3. Экран подопечных и быстрых событий; реальное сохранение с серверным подтверждением.
4. PDF/отчеты, напоминания и семейный доступ отдельным этапом.
